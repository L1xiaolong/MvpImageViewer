# Windows 恢复大 YUV 目录时的启动崩溃分析

## 现场与结论

2026-10-11 检查用户提供的目录
`C:\Users\home\Desktop\M100相机模组V3性能摸底测试20261010\摸底图片`：
共 75 个 YUV 文件，每个 72,000,000 字节，总计约 5.03 GiB。
文件名推断为 8000×6000，默认 NV12，单帧大小与文件长度一致。
无头 YUV 不能仅凭文件内容确认格式；这里沿用软件现有的参数推断规则。

用户补充：故障机器有 40 GB 内存，笔记本集成显卡，保存的是网格模式。
因此不能直接把主因归结为系统内存不足。当前机器未复现原始闪退，
也没有故障机器的转储；以下是已确认并修复的代码缺陷及验证结果，
不是对故障机器异常指令的最终定位。

## 1. 缩略图响应完成通知与回收存在竞争

网格使用 `ThumbnailTile.qml` 的异步 `Image`，请求 384×384 缩略图，
经 `ThumbnailImageProvider` → `ImageLoader` → `AccountedTextureFactory`
交给 Qt 场景图。它不会把每个 8000×6000 YUV 的原始平面上传到显卡。

旧流程存在明确的生命周期问题：

1. Qt 图片读取线程创建 `ThumbnailImageResponse`，对象属于该线程。
2. `start()`、加载器回调和 `finish()` 在 GUI 线程执行。
3. 内存缓存命中或文件验证失败时，`ImageLoader::request()` 同步回调。
4. 回调立即发出 `finished()`，Qt 可在图片线程读取纹理工厂并回收响应。
5. `request()` 返回后，`start()` 还会锁响应的互斥量、写入 `handle_`，
   与对象回收竞争。已经排队的 GUI 回调也可能与图片线程删除对象竞争；
   `QPointer` 的空值检查不能锁住对象寿命。

Qt 对完成信号的约定是：发出信号必须是响应的最后一个动作。
参见 [QQuickImageResponse 文档](https://doc.qt.io/qt-6/qquickimageresponse.html)。
该缺陷可以导致访问已释放内存或锁住已销毁的互斥量，表现取决于线程时序。
它与设备速度相关的偶发故障相符，但是否触发了现场崩溃还需要故障机器验证。
冷启动中首次请求也可能因视口、参数或模型更新而发生重复请求与取消。

修复：响应在创建线程内移到加载器的 GUI 线程，Qt 的 `deleteLater()`
也在 GUI 线程执行；所有解码结果经响应自身的排队调用交付，确保
`start()` 返回、句柄安装完成后才发出完成信号。取消仍立即通知共享解码任务，
完成通知排队到 GUI 线程。同步兼容接口也改为按响应所属线程延迟删除。

## 2. 小缩略图读取完整大帧，放大启动负载

旧解码器即便只生成 384 像素缩略图，也为每个文件读取完整 72 MB 帧，
并尝试保留源数据缓存。线程池、源缓存、结果交付和 Qt 图片转换叠加时，
会制造不必要的内存、磁盘读和分配压力。这是已确认的负载问题，
不足以单独证明 40 GB 故障机器发生了内存耗尽。

修复：YUV 缩略图与预览按需读取采样行，每个平面最多保留 4 行，
保留原来的色度插值、矩阵、范围、帧偏移、步长、字节序和旋转规则。
支持 NV12、NV21、I420、P010。完整查看仍读取完整帧；Bayer 流程保持原样。
缩略图与预览不再向源缓存写入完整 YUV 帧。

同时让解码工作内存和待交付结果预算随加载器预算调整，
捕获工作线程中图像准备/记账阶段的分配异常，返回失败并释放任务槽位。
结果预算先分配占用令牌、再登记字节，避免令牌分配失败造成预算泄漏。
这些保护不等同于能够从任意系统级内存耗尽中恢复。

## 3. 原生 GPU 资源失败后仍继续使用

完整查看/对比使用 `QmlImageCanvas`，旧实现部分资源 `create()` 失败后
只记录日志，仍会提交纹理上传、绑定或绘制。大图可能超过设备纹理尺寸上限，
集显也可能拒绝某些格式或资源分配。

修复：先检查纹理尺寸上限和格式支持，原生 YUV/Bayer 纹理失败时释放部分资源，
使用已有 CPU 显示图回退；显示纹理分配失败时尝试 256 像素 RGBA8 回退。
必要资源仍失败时停止相关提交，清空画布并记录失败。
这主要保护完整查看/对比，不应作为网格启动闪退的已确认原因。
Qt 的纹理创建失败契约见 [QRhiTexture 文档](https://doc.qt.io/qt-6/qrhitexture.html)。

Windows 原有默认 OpenGL 和显式环境变量覆盖逻辑保留。
没有证据支持盲目切换到另一驱动路径。
主窗口的 `scenegraph.initialized` 现在同时记录 GPU 名称、设备类别、
纹理尺寸上限，网格启动也能提供这些信息。

## 验证

Windows Release 已构建成功，当前环境 Qt 6.11.0、MinGW。
开启 `MVPVIEW_BUILD_TESTS` 后，4 项 CTest 全部通过：

- `yuv_startup_regression`：64 种格式/尺寸/步长/偏移/旋转等组合比较
  行读取和完整帧读取的像素；测试取消、截断文件、分配异常后的任务恢复。
- `browse_restore_regression`：隔离设置和磁盘缓存，调用实际
  `restoreInitialDirectoryAsync()` 入口恢复目录，经过真实图片提供器生成缩略图。
  对用户的真实目录也运行成功，75 个 384 像素缩略图全部完成。
- `thumbnail_response_regression`：1,200 次模拟 Qt 图片读取线程的请求，
  包括内存缓存命中、启动前取消、安装句柄后取消，完成时立即回收响应。
  新版通过；使用 HEAD 旧图片提供器的对照程序通过冷加载后，在缓存命中
  寿命压力阶段超过 10 秒未完成，被测试超时终止。
  这是代码缺陷的回归证据，不是现场同一崩溃的复现。
- `rhi_fallback_regression`：Null RHI 上构造超出纹理尺寸上限的 YUV，
  验证 CPU 回退完成并重建资源，名义 GPU 占用 154,656 字节。

另外在进程提交内存上限 128 MiB、加载器预算 32 MiB、全新磁盘缓存下，
生成真实目录全部 75 个 256 像素缩略图成功。
测得图像常驻记账峰值 14,745,600 字节，进程提交峰值 55,431,168 字节。
这是解码压力测试，不是整个 GUI/GPU 的内存测量。
8000×6000 → 256 像素缩略图的解码预留为 1,636,864 字节。
旧解码器对照失败于“缩略图仍保留完整源帧”检查。

真实目录的软件场景图主界面截图已检查，网格缩略图显示正常。
当前离屏平台不支持创建 OpenGL 上下文，所以硬件 OpenGL 主界面测试受限。
Null RHI 测试也不代表 Intel 集显驱动验证。故障设备仍需要用匹配 Qt 运行库的
新构建做重复启动复测；若仍闪退，从“设置 → 日志与诊断”导出资料并勾选
“包含崩溃转储”，结合对应构建符号确认故障模块和地址。

## 本地复测命令

在仓库根目录，以项目现有的 Windows 工具链配置构建：

```powershell
cmake -S . -B build/windows-msys2-release -DMVPVIEW_BUILD_TESTS=ON
cmake --build build/windows-msys2-release -j 4
ctest --test-dir build/windows-msys2-release --output-on-failure
$env:QT_QPA_PLATFORM = 'offscreen'
& ./build/windows-msys2-release/browse_restore_regression.exe 'C:\Users\home\Desktop\M100相机模组V3性能摸底测试20261010\摸底图片'
& ./build/windows-msys2-release/yuv_startup_regression.exe 'C:\Users\home\Desktop\M100相机模组V3性能摸底测试20261010\摸底图片' 128
```

测试使用仓库内临时目录隔离设置/缓存，不修改真实 YUV 文件。
测试开关默认关闭，不影响正常发行构建。
